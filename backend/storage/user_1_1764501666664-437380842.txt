## 1. Abstract

This report details the design, architecture, and implementation of a high-performance, browser-based Augmented Reality (AR) application. The system successfully demonstrates real-time image tracking and **Six-Degrees-of-Freedom (6-DOF) pose estimation** to overlay a complex 3D digital model onto a physical-world fiducial marker. The project’s architecture leverages a decoupled, multi-layered stack, integrating a specialized computer vision engine (Mind-AR.js) with a declarative 3D rendering framework (A-Frame). The final solution is deployed as a lightweight, client-side application that runs on any modern web browser, eliminating the need for a native app-store installation and demonstrating a highly accessible, low-friction model for AR deployment.

## 2. Project Architecture

The application was not built as a single monolith, but rather architected as a series of interconnected layers and modules that work in concert.

### Layer 1: The Client-Side Application (`index.html`)
This is the primary entry point for the user. This core module is responsible for:
* **Structuring the Scene:** Defining the Document Object Model (DOM) and the overall structure of the AR experience.
* **Module Integration:** Managing the asynchronous loading and initialization of all other framework dependencies.
* **Scene Graph Definition:** Declaring the 3D scene, its assets, and the hierarchical relationships between them.

### Layer 2: The Computer Vision Engine (Mind-AR.js)
This is the "brain" of the operation, a specialized JavaScript library responsible for all computer vision tasks. Its operations are computationally intensive:
* **Camera Pipeline:** It interfaces directly with the device's `WebRTC` API to acquire and process the live video feed.
* **Feature Detection:** The engine constantly scans the video stream for a specific pattern of feature points. These points are derived from the `card.mind` file, which is a **pre-compiled feature point database** generated from the original `card.png` marker.
* **Pose Estimation:** Upon detection, the engine calculates the marker's precise 3D position (X, Y, Z) and 3D rotation (pitch, yaw, roll) in real-time. This is a complex **6-DOF pose estimation** that provides the foundation for the AR illusion.

### Layer 3: The 3D Rendering Engine (A-Frame)
A-Frame (built on Three.js) serves as the high-level rendering engine. It simplifies the complex WebGL API using an **Entity-Component-System (ECS) architecture**.
* **Entity:** The "things" in our scene, such as the camera, the 3D model, and the light (`<a-entity>`).
* **Component:** The "properties" we attach to them, such as position, rotation, 3D geometry, and materials.
* **System:** Global-scope processes that manage components, such as the `mindar-image` system that bridges the gap between the vision engine and the 3D scene.

### Layer 4: The Asset & Dependency Pipeline
A critical part of the project was managing the delivery of assets and libraries in a scalable way.
* **Library Delivery:** The A-Frame and Mind-AR frameworks are injected into the application's runtime via a **Content Delivery Network (CDN)**. This ensures low-latency delivery by serving the files from a geographically distributed server cache.
* **Asset Delivery:** The 3D model (`.gltf` format) and marker database (`.mind`) are also hosted and delivered via CDN, reducing initial load times and separating the application logic from its static assets.

## 3. Project Development Methodology

The project was executed in several distinct phases, following a structured development lifecycle:

### Phase 1: Environment & Framework Configuration
The initial phase involved setting up a robust local development environment. A `Node.js`-based server (VS Code Live Server) was used to emulate a production environment, which is a critical requirement for handling camera permissions (`WebRTC` requires a secure `https` or `localhost` context) and managing cross-origin asset requests.

### Phase 2: Vision Target Compilation
This was a key pre-processing step. The target image (`card.png`) was analyzed to extract its unique visual feature points. These points were then compiled into a highly-optimized `.mind` database. This offline compilation is what enables the library to perform high-speed, real-time matching on the device, as the heavy computational work is already done.

### Phase 3: Scene Graph Implementation
Using A-Frame's declarative ECS syntax, the 3D scene graph was architected. This involved:
1.  **Scene Initialization:** Configuring the main `<a-scene>` element and integrating the `mindar-image` system.
2.  **Asset Management:** Defining all 3D models and textures in the `<a-assets>` block to ensure they are pre-loaded before the AR experience begins.
3.  **Camera Setup:** Configuring a virtual camera that would be programmatically controlled by the Mind-AR engine.

### Phase 4: AR Anchor Integration
This is the core of the project's logic. An anchor entity (`<a-entity mindar-image-target>`) was created. This entity acts as a digital "hook" in the 3D space. The Mind-AR engine continuously feeds its 6-DOF pose estimation data *to this anchor*.

By parenting the 3D model (`<a-gltf-model>`) as a *child* of this anchor, we automatically link the model's transform (its position and rotation) to the physical marker's transform. This ensures the 3D model appears perfectly "stuck" to the card.

### Phase 5: Testing, Debugging, and Refinement
The final phase involved iterative testing. This included:
* **Tracking Stability:** Testing the tracking robustness under different lighting conditions and at various angles.
* **Model Scaling:** Adjusting the scale, position, and rotation of the 3D model to ensure it was properly aligned with the marker.
* **Performance:** Verifying a smooth framerate and responsive tracking.
